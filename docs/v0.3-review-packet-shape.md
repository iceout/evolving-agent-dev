# v0.3 Review Packet Shape

Status: draft shape.

## Purpose

This is a lightweight review target and handoff artifact, not a longer prompt. Use it only when a plan needs independent review, multi-round review, cross-agent handoff, later implementation, or high-risk implementation review. Small tasks do not need a packet.

Every packet needs the goal and scope boundaries (including changed files or diff scope), relevant risks and reviewable constraints, known user decisions or exceptions, and a verification path. Combine these into short sections when useful. Other sections are conditional: omit ordinary inapplicable sections and explain exclusions only when they affect acceptance or review. Real-code packets use `skills/coding-review-loop/references/review-packet-shape.md`, including its explicit conditional risk exclusions.

Future subagent or automation review should consume packet artifacts, not raw chat context.

## Shape

### Goal

What outcome should the task produce?

### Non-goals

What is intentionally out of scope?

### User Decisions and Exceptions

Record explicit user choices, accepted exceptions, privacy/output exceptions, and decisions that reviewers should not reopen unless new evidence appears.

### Risk Surfaces

List the relevant surfaces, such as public interface, hot path, schema/contract, data semantics, sensitive output, batch/action/export, time/window, config/deployment, or multi-module docs/tests changes.

### Debug / Bad-Case Evidence Chain

For a bad case, missed detection, wrong score/selection, surprising output, or similar example, capture observed symptom, expected behavior, affected contract, candidate failure points, source-of-truth data, blockers/filters, and real verification path.

### Reviewable Constraints

State the constraints the implementation or review must preserve. Prefer bullets that can be checked against code, tests, docs, or runtime behavior.

### Task-Specific Contracts

Include only relevant contracts; explain an exclusion when it affects acceptance or review.

- Collection/cardinality/counting.
- Failure/status/degraded behavior.
- Schema/API/output contract.
- Time/window semantics.
- Privacy/sensitive output.
- Source-of-truth/proxy/fallback.
- Mitigation vs final redesign.

### Reuse / Adapter Rationale

Name the existing helper, builder, adapter, serializer, guard, or pattern being reused. If adding a new one, explain the distinct responsibility and why existing same-concern code does not fit.

### Required Behavior Tests

List behavior-level tests or manual checks required to prove the contract. Avoid implementation-detail assertions unless justified.

### Verification Plan

Record the real verification path: tests, lint/typecheck, manual runtime checks, production-like review, or explicit verification limits.

### Implementation Trace

Maintain one evolving trace: requirement -> planned or actual artifact -> behavior test or verification -> cross-artifact check. Update planned anchors with implementation anchors and actual results rather than creating another table. For plan-only work, implementation and verification results remain pending.

### Independent Reviewer Checklist

List the few questions an independent reviewer should answer before approval.

### Open Questions / Risks

Record unresolved choices, accepted risks, rollout-only checks, or items that need user review before implementation.
