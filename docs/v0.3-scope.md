#### CRL-X06 - Multi-step mutation integrity

- Sources: `ext-crl-2026-07-b/C01` and `C02`; one external privacy-preserving evidence batch from the same task's review-fix and follow-up review stages. The two related findings are not independent repetitions.
- Normalized parent pattern: multi-step mutable-state workflows need two evidence-backed protections. Preflight-detectable completion blockers are checked before the first mutation, and rejection at that stage leaves relevant state unchanged. Each independently mutable boundary has an explicit concurrency and consistency contract with an appropriate guard; protection at one boundary does not protect another. When optimistic concurrency is used, each boundary validates its own expected old state.
- Interpretation boundary: preflight-rejection no-op behavior does not imply universal workflow atomicity. Failures that can arise only after mutation begins may instead require rollback, compensation, idempotent retry, or accurate partial-state reporting. This batch does not establish or verify a generic post-mutation recovery requirement.
- Related sub-issues: `C01` observed precondition ordering before mutation for a preflight-detectable blocker. `C02` observed per-boundary expected-old-state protection as the appropriate optimistic-concurrency mechanism in the source workflow; the generalized concern is an explicit concurrency and consistency contract at every independently mutable boundary.
- Root-cause hypothesis: the initial packet did not make preflight ordering, preflight-rejection no-op behavior, or per-boundary concurrency and consistency contracts explicit. Observed review detection was effective. Current canonical guidance is directionally aligned with that behavior, but loaded-version evidence is unavailable, so detection is not attributed to a specific rule version. Confidence: medium; both observations come from one task.
- Prevention and detection: plan/packet prevention was incomplete; independent review detection was effective through a no-write forward scenario for `C01` and adversarial concurrency review for `C02`. Regression prevention and final fix verification are not established by the transferred note.
- Repository rule state: `partial`; the canonical skill requires high-risk review, failure modes, reviewable constraints, and behavior tests, but does not explicitly cover preflight ordering, preflight-rejection no-op behavior, or per-boundary concurrency and consistency contracts.
- Source-task attribution: `loaded version unknown`; the note names the skill but does not record a reliable loaded source or version, and the task date does not establish one. This is not evidence that a known present rule was skipped.
- Decision/change: no generic skill change for now. The findings are correlated within one task, independent review successfully detected both, and implementation-specific concurrency mechanics do not belong in the generic skill. Do not change `CRL-X01`, `CRL-X02`, or `CRL-X03`, and do not change the current active priority.
- Later comparable evidence: none.
- Next decision: inactive high-impact discovery candidate, not an active learning bet. Do not start a synthetic pilot; wait for one independent real case from another domain covering preflight ordering or per-boundary consistency before deciding whether to add a generic packet contract. If a post-mutation recovery case arises naturally, assess separately whether it belongs in this lineage.
- Outcome: `awaiting evidence`; an explicit no-change decision exists, but there is no later comparable evidence from a known relevant version.
- Boundaries: external evidence only; not Stage 0 evidence and not promoted to policy, ADR, casebook, or formal evaluation.

### Evaluation Candidate Watchlist

- Focused reuse scan before adding helpers, fakes, wrappers, adapters, serializers, collection getters, fallbacks, or test doubles:
  - Candidate behavior: Agent should search same-file and sibling modules/tests before adding or changing same-concern helpers, especially during review-fix work.
  - Missing before promotion: privacy-safe fixture, expected-pass rubric, expected-fail examples, and judge method.
- Source-of-truth/fallback semantics:
  - Candidate behavior: Agent should verify docs, config, runtime evidence, or existing source helpers before encoding fallback behavior or data-source selection as a tested contract.
  - Missing before promotion: fixture showing an incorrect fallback temptation, visible source-of-truth evidence, and pass/fail criteria.
- Action/report semantic liveness:
  - Candidate behavior: Agent should verify acceptance-critical action, report, and enum-like values have a producer, consumer, and behavior test before treating a contract as alive.
  - Missing before promotion: privacy-safe fixture with a structurally present but unreachable business value and clear pass/fail rubric.
- Config-driven report truthfulness:
  - Candidate behavior: Agent should separate config labels from validated behavior and require bounds or negative tests before report output implies actionable recommendations.
  - Missing before promotion: privacy-safe fixture with misleading config labels, expected validation failure, and judge method.
- Semantic-responsibility reuse scan:
  - Candidate behavior: Agent should search by helper responsibility, not only feature keywords, and prefer existing source-of-truth helpers plus caller-local state before adding a new helper.
  - Missing before promotion: privacy-safe fixture with an existing source helper, a tempting duplicate, and clear abstraction-value criteria.
- Test double boundary fidelity:
  - Candidate behavior: Agent should fake the lowest practical external IO boundary and keep fake call shapes faithful enough to catch repo-owned helper contract regressions.
  - Missing before promotion: privacy-safe fixture where a middle-layer mock hides a call-signature regression.
- Dataflow contract preservation:
  - Candidate behavior: Agent should trace time-windowed, streaming, paginated, batched, deduped, or source-filtered contracts through callers.
  - Missing before promotion: privacy-safe fixture where helper shape is correct but caller widens, materializes, or recomputes from the wrong source.
