# v0.4 Scope Note

Status: scope draft. Not an authorized work plan.

This note proposes a direction. Writing it does not authorize deleting a rule,
retiring a skill, changing a CRL lineage outcome, or starting an evaluation
pilot. Each item below names the decision it still needs.

## Relationship to Stage 0 and v0.3

- Stage 0 counts remain frozen. Nothing here is Stage 0 evidence.
- v0.3 remains the current refinement and external-evidence state. Its CRL-X01
  through CRL-X07 outcomes, evaluation watchlist, and evidence boundaries are
  unchanged by this note.
- v0.4 is about the collection as a whole: which guidance is still load-bearing,
  what the evidence loop should measure, and what should be removed. v0.3 was
  about improving individual rules in place.

## Why This Scope Exists

The rules in this repository were largely written against an earlier generation
of agent behavior. Some of them encode corrections that current models rarely
need. Others encode real, recurring failures that came from missing project
facts rather than from agent disposition. The collection has never retired
anything, so it can only grow, and its length is now a cost in its own right.

The claims below are hypotheses with cited repository evidence, not established
findings. Each names what would show it is wrong.

## Diagnosis

### D-1. Rules accumulate; none retire

**Observation.** The lifecycle already defines `proposed` / `active` /
`deprecated` / `superseded`, but no rule, policy, checklist item, or skill has
ever moved to `deprecated` or `superseded`. Both policy notes in `docs/policies/`
remain `proposed` since June.

**Evidence.** `docs/process-v0.2.md` defines the lifecycle. `docs/v0.3-scope.md`
records seven lineages whose dispositions are all `awaiting evidence`,
`inconclusive`, or `implemented / awaiting evidence`; none is `improved`.
CRL-X02's own pilot produced identical patches from both snapshots and was
recorded as `no incremental signal`, yet the rule remains in the canonical skill
with no retention criterion.

**Why it matters.** Without a retirement path, every refinement is additive. The
canonical skill's cost per invocation keeps rising while the evidence that any
specific item works stays at zero. This is in tension with
`docs/principles.md` principles 2 and 10.

**Would be wrong if.** A retrospective check shows individual rules were in fact
removed or rewritten when evidence was weak. No such record exists in the
repository, but absence of a record is not proof of absence.

### D-2. The evidence gate cannot close

**Observation.** The admission conditions for a comparable observation are
individually defensible and jointly almost unsatisfiable: a known loaded
version, a natural (not synthetic) task, prior independent designation, a real
opportunity for the behavior to fail, and post-change comparability. Every
condition exists to prevent overclaiming. The aggregate effect is that the loop
produces records but not conclusions.

**Evidence.** `skills/coding-review-loop/SKILL.md` (Case Note Capture) requires
prior independent designation and rejects self-designation; local task-start
attribution requires a timely receipt that is not a platform attestation, but
ordinary tasks no longer collect it by default; `docs/v0.3-scope.md`
records that every lineage still awaits such evidence. `docs/skill-design/local-evidence-ledger.md`
documents the same constraint for target-project notes.

**Why it matters.** The measured question has become "is this attribution
defensible?" rather than "did this rule change behavior?". A test that cannot
pass or fail does not protect quality; it consumes the budget that would.
`docs/principles.md` principle 9 commits this project to evaluation over prompt
guessing, and the current gate is the reason no evaluation runs.

**Would be wrong if.** A known-version natural observation has occurred and been
correctly classified. None is recorded as such.

### D-3. Infrastructure compensates for capabilities the runtime now provides

**Observation.** A large share of the repository's operational surface exists to
answer questions that the current runtime answers natively: which version of a
skill is loaded, how to hand context to an independent reviewer, how to install
and verify a package.

**Evidence at diagnosis.** `skills/coding-review-loop/SKILL.md` formerly required
running a packaged fingerprint script at first use of every non-trivial task
and again at capture, while stating that the result was not an audit of model
loading or rule execution. `README.md` documents an install/inspect/compare flow
around `scripts/install-skill.py`. ADR-0002 encodes a manual analysis-then-
forwarding workflow whose justification was user coordination cost.

**Why it matters.** Each of these is a per-task cost with an explicit,
self-declared attribution limit. The identity helper has been in place since
2026-09-16 and has not produced one classified observation. The current direction
should be: use runtime-native mechanisms where they exist, and keep only the part
that is genuinely this project's evidence — the privacy boundary and the
narrative record.

**Would be wrong if.** A future runtime change removes native version or
context-isolation capability, or real task records show the fingerprint receipt
routinely made attribution possible when nothing else would have.

**Current state.** Identity collection is now an on-demand audit. Ordinary tasks
and friction cases need no fingerprint; known-version observation claims still
need a contemporaneous attribution basis or an authority-supplied version.
See the [D4 maintenance report](session-reports/2026-11-17-on-demand-skill-identity.md).
No native runtime attestation is assumed or introduced by this change.

### D-4. Guidance is duplicated and oversized

**Observation at diagnosis.** The same packet shape was maintained in two
places, and the canonical skill carried long conditional prose for rules whose
triggers are rare. Packet duplication is now resolved; the inline-guidance
concern remains open.

**Evidence.** `docs/v0.3-review-packet-shape.md` and
`skills/coding-review-loop/references/review-packet-shape.md` were parallel
documents with divergent text (a prior session found conflicting N/A
guidance in exactly this pair, recorded in
`docs/session-reports/2026-09-08-skill-friction-and-version-visibility.md`).
`skills/coding-review-loop/SKILL.md` carries its advanced rules as conditional
paragraphs that must be read on every use, although `Read references/...` only
on demand is already the established pattern.

**Why it matters.** Divergence between the two copies is a known failure mode in
this repository, and long inline conditional prose spends attention that the
on-demand reference-loading pattern would not.

**Current state.** The skill reference is the sole maintained packet shape.
The repository document is a compatibility pointer with no independent fields;
existing process-skill instructions reach the reference through that pointer.
See the [consolidation report](session-reports/2026-11-17-packet-shape-single-source.md)
for coverage and link checks. The skill packages themselves were not changed.

**Would be wrong if.** Repository-wide packet-shape duplication is limited to
these two files and the divergence is confined to the N/A wording.

## Proposed Direction

Each item is a proposal. None is authorized by this note.

Apply [principle 11](principles.md#11-maintain-prompts-and-process-rules-as-ordinary-engineering-changes)
to maintenance decisions: D-4 document deduplication and D3/D4/D5 changes do not
require D1 or another A/B experiment. Maintainer review and risk-proportionate
verification may establish equivalent behavior or accept an explicit behavior
change, with a recovery path. Effectiveness and internalization claims remain
separate evidence questions. This principle does not authorize the individual
implementation proposals in this scope draft.

### D1. Optional baseline re-test for uncertain behavior hypotheses

Screen the selected guidance items with one fixture each. Run the current model
without and with registered verbatim rule excerpts, several times per
fixture; judge against a frozen pass/fail rubric written before the runs.
Classify each item as `internalized` (the model passes without the rule),
`load-bearing` (the rule changes the outcome), or `harmful` (the rule causes a
regression such as over-triggering).

Design: [the D1 rubric](skill-design/d1-baseline-retest-rubric.md) and
[the D1 fixture list](skill-design/d1-fixture-list.md). Freeze execution inputs,
with hashes, before running an experiment. The
[first minimum-cut pilot](session-reports/2026-11-16-d1-min-cut-stage1.md)
closed at Stage 1 without confirmed classifications or retirement support.
The full design contains eleven guidance-screen fixtures, two separate runtime
checks, and one negative control. Deferred or runtime-only items cannot be
retired on the basis of this screen.

Boundary: this measures explicitly exposed canonical guidance text at fixture
level, not natural skill activation or reference discovery. Existing policy and
reference probes are not mandatory-path retirement candidates. It does not
produce real-task improvement claims and creates no lineage. Its output is a
keep / revise / demote candidate for each tested item, recorded in the session
report, conditional on the evidence-tier decision below.

Use this when the decision needs a behavior check: it screens the "current models have internalized this"
hypothesis and informs D-1 retirement candidates. It does not test or close D-2:
synthetic results do not satisfy the real-task admission gate. Their institutional
use depends on explicitly accepting the two evidence tiers below.

### D2. Make retirement normal

Review whether an item belongs in the per-task read path using its purpose,
known failures, attention cost and overlap with other guidance. Maintainer review
may approve removal, revision or demotion to a reference without a fixture
classification, with appropriate verification and a recovery path. Neither
retention nor removal requires proof of effectiveness or ineffectiveness.

If fixture classifications are cited, their decision use remains subject to
the two evidence tiers and the experiment's validity limits. A result labeled
`internalized` or `harmful` can inform a proposal, not automatically authorize
an edit or prove prevention. A maintenance decision must not be presented as
such a classification when the experiment did not establish it.

The existing status vocabulary is sufficient; what is missing is that no decision
is required. That requirement, not a new vocabulary, is the change.

### D3. Separate "what the model should do" from "what this project must say"

The recurring real failures in `docs/casebook/inbox.md` and the CRL lineages are
dominated by missing project facts: source of truth, gate compatibility, runnable
entrypoints, target version. Those are not model-behavior defects and they do not
generalize. The packet should ask the task author to supply them, rather than
instructing the agent to remember to look for them.

Concretely: packet fields phrased as questions the project must answer, plus
evidence slots, in place of imperative reminders in `SKILL.md`.

### D4. Delete runtime-compensating ritual from the hot path

- Completed in canonical guidance: skill identity is an explicit on-demand audit
  command, not a mandatory first-use or ordinary case-capture step. See the
  [maintenance report](session-reports/2026-11-17-on-demand-skill-identity.md).
- The install/inspect/compare flow is reduced to what still helps a human
  maintainer; package loading itself is not this repository's problem.
- ADR-0002's orchestration is retained as an explicit-request path, not a
  default workflow.

The privacy rules and the "record facts, not private data" boundary stay. They
remain this project's distinct contribution.

### D5. Shrink the skill surface

Target shape: one on-demand packet-shape reference, one review rubric, one
root-cause gate. `idea-framing-loop` and the packet references overlap enough
that this needs its own decision rather than an assumption; flagging it here
only.

This item can proceed through maintainer review and targeted verification
without D1. Keep sufficient trigger wording in the main skill to make the
on-demand guidance discoverable, and review any intended change in visibility.

### D6. Change the unit of a session report

Propose one hypothesis, one check, one conclusion per report, with an explicit
`no conclusion reached` bucket that is counted and reviewed rather than repeated.
Current reports frequently record that nothing was established; that is honest
and should stay possible, but it should be visible as a rate.

## Decision Gates

These require explicit user authorization and are not implied by this draft:

- Before D1 execution, explicitly accept or reject two evidence tiers: (a)
  fixture screening, usable only for keep/demote/revise candidates; (b) known-
  version comparable real tasks, required for effectiveness claims. Without
  acceptance, D1 results remain instrument observations with no D2 decision use.
  This restricts claims based on D1, not maintenance decisions under principle 11.
- Any deletion or demotion of canonical skill guidance.
- The on-demand identity change under D4 was explicitly authorized and is
  implemented; this gate no longer blocks removing the former first-use step.
- Retiring or merging a skill package.
- Promoting or reclassifying any CRL lineage outcome.
- Creating a formal evaluation from any watchlist candidate.
- Rewriting `docs/process-v0.2.md` or producing a `docs/process-v0.3.md` /
  `process-v0.4.md` specification.

## What Should Be Preserved

- The friction taxonomy in `docs/process-v0.2.md`. It is model-independent and
  has reused well.
- Review packets as a handoff artifact. This became more valuable, not less, as
  subagent review became cheap: the bottleneck moved from review availability to
  review context.
- Root-cause gate, focused reuse scan, test-double boundary fidelity, semantic
  liveness, dataflow contract preservation. These correspond to real failures
  observed in external code, independent of model generation.
- The privacy and evidence-boundary discipline. It is the part of this repository
  that is hardest to rebuild elsewhere.

## Open Questions

- Should `internalized` items be kept for weaker execution surfaces, and if so
  where, given the existing non-goal against a second ledger?
- Does the memory tooling in use (`memory search` / `memory add` / `memory apply`)
  belong in the broader loop, or is it a separate trial with its own questions?
  D1 pins memory off in both conditions regardless of that future decision.
- How should a retirement be recorded so that `docs/v0.3-scope.md` remains
  readable as current state rather than becoming a historical archive?
